Los códigos RF y CU/FE/PE identifican requisitos y pruebas para el equipo; puedes seguir los enlaces a las fichas para leerlos explicados. [01-PROYECTO.md](01-PROYECTO.md#cómo-leer-los-requisitos) explica los términos más frecuentes.

## Procedimiento para la siguiente IA o colaborador

1. **Entrada:** leer [AGENTS.md](../AGENTS.md) y las skills que exige para el trabajo. Abrir esta ruta para elegir el primer paso sin verificar; confirmar su dependencia en el [mapa](../MAPA-CAPACIDADES.md). Revisar `git status` antes de editar.
2. **Contexto de producto:** leer [01-PROYECTO.md](01-PROYECTO.md) para el problema, actor, RF y RNF del paso; después [03-DECISIONES.md](03-DECISIONES.md) para separar acuerdos de preguntas abiertas. Abrir la [ficha enlazada arriba](ESPECIFICACIONES/00-INDICE.md) y localizar flujos, entradas, validaciones, errores y criterios con ID.
3. **Realidad técnica:** comparar la ficha con código, [05-API.md](05-API.md) y [04-DATOS-Y-PERMISOS.md](04-DATOS-Y-PERMISOS.md). Anotar qué está presente, qué falla y qué no se verificó. Usar [README.md](../README.md) para comandos y entorno. Actualizar «Integrado hoy» si la evidencia cambió.
4. **Especificación:** aplicar [02-SDD.md](02-SDD.md). Revisar con el usuario la ficha y sus preguntas abiertas que afectan el alcance. Una vez aprobado el comportamiento, documentar datos, permisos y navegación necesarios en el plan; no decidir columnas o flujos por inferencia.
5. **Plan y tareas:** crear o revisar `01-PLAN.md` y después `02-TAREAS.md` del módulo, con dependencias, archivos, riesgos y una prueba por tarea. Cada puerta SDD se revisa para esa capacidad; los planes/tareas históricos se contrastan con la ficha vigente.
6. **Implementación y validación:** trabajar una tarea aprobada a la vez, verificar permisos y estados de éxito, vacío y error, y reunir evidencia por criterio en API, datos y app cuando corresponda. Actualizar ficha, API, datos, decisiones y esta ruta. Solo marcar «Verificada» después de comprobar todos sus criterios.
