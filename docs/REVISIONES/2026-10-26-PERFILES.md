# Perfiles: integración funcional y verificación local — 26-10-2026

El usuario autorizó completar las funciones faltantes de Perfiles y revisar después UI/UX. Mi perfil permite editar datos y foto y ahora ofrece desactivar la cuenta con confirmación. Si falta otra persona administradora en alguna comunidad, muestra el motivo y accesos para gestionarla. Solo cierra sesión después de la confirmación del servidor.

La implementación funcional está integrada. PE-T01–PE-T10 quedan comprobadas localmente. PE-T11–PE-T13 tienen código y comprobaciones locales, pero conservan su casilla abierta por el recorrido físico pendiente. PE-T14 tiene informe y regresión local completos y espera esa evidencia final. No se presenta Perfiles como «Verificada» de punta a punta ni se atribuyen pruebas nuevas en iPhone al usuario.

## Cambios y permisos

- `POST /users/me/deactivate` usa exclusivamente la identidad de sesión, admite `{}` y rechaza campos ajenos, incluido `userId`. Confirma con 200 y `{ isActive: false, message }`.
- Comprueba todas las comunidades administradas y cuenta únicamente otros `ADMIN` activos. Si alguna quedaría sin responsable, devuelve 409 con `code: LAST_ACTIVE_COMMUNITY_ADMIN`, explicación y `communities: [{ id, name }]`; no cambia parcialmente la cuenta.
- La comprobación y desactivación usan aislamiento Serializable. Creación de comunidades, membresías, salidas y cambios de rol participan también en ese aislamiento, manteniendo el bloqueo existente por comunidad. Se reintentan como máximo cuatro veces los conflictos de serialización/interbloqueo, incluidos errores originales del adaptador Prisma 7 al confirmar; los demás errores se conservan.
- Se puede repetir una desactivación cuya respuesta se perdió: exige JWT válido, sesión reconocida por Supabase y correo confirmado y devuelve solo la confirmación mínima. Esta excepción específica no permite acceso a contenido a una cuenta inactiva.
- Solo cambia `User.isActive`: no se borran contenidos, fotos, membresías ni roles. Mascotas, publicaciones, fotos protegidas, comentarios, likes y miembros respetan el estado de cuenta. Reactivar comprueba de nuevo correo y contraseña y recupera la misma cuenta; mascotas, publicaciones y comentarios retirados individualmente siguen retirados.
- La app muestra espera, bloqueo, error y reintento. Comparte un bloqueo de envío entre guardar datos, modificar foto y desactivar, evitando también abrir dos selectores. Los errores y las respuestas de guardado no borran un borrador posterior.
- Renovar la sesión correctamente en segundo plano mantiene las pantallas montadas. Una versión de sesión y una cola de SecureStore impiden que un refresh atrasado reponga tokens tras salir/desactivar, sobrescriba una reactivación o que la respuesta de otra cuenta cierre la actual. Credenciales de reactivación solo en memoria: se descartan al terminar, salir o rechazar las credenciales.
- Perfil propio, detalle público y búsqueda descartan respuestas atrasadas al salir/cambiar de consulta y evitan duplicados al paginar. El detalle público consulta mascotas por su contrato existente, sin correo ajeno.

No se añadieron columnas, tablas, migraciones, proveedores ni buckets. Se mantiene NestJS/Prisma como vía de datos. No se desactivaron cuentas de la base compartida ni se modificó Supabase para estas pruebas.

## Entorno, comandos y resultados

PostgreSQL desechable local con las nueve migraciones existentes. Las nuevas pruebas usan el guard real; JWT/JWKS, Supabase Auth y bytes de Storage están simulados. No equivalen a comprobar proveedores o dispositivo reales.

- HTTP completo: **9 suites, 58 pruebas aprobadas**, con `node --experimental-vm-modules node_modules/jest/bin/jest.js --config test/jest-e2e.json --runInBand --silent` y `POST_TEST_DATABASE_URL` local.
- Unitarias: **17 suites, 102 pruebas aprobadas**, con `node --experimental-vm-modules node_modules/jest/bin/jest.js --runInBand --silent`. Los errores de Storage impresos corresponden a fallas provocadas por las pruebas.
- Compilación Nest y TypeScript móvil aprobados.
- ESLint de los archivos cambiados y de todos los directorios fuente móviles (`app components constants context hooks lib scripts types`) aprobado, sin errores ni advertencias. `pnpm --filter mobile verify:profiles` ejecuta los scripts nuevos de sesión y pantalla sin dependencias nuevas. La regresión `verify:interactions` también pasa.
- Exportación iOS aprobada: **1613 módulos**; es empaquetado local, no instalación ni ejecución física.
- Lint completo detectó además un problema previo de hidratación del tema web e imports sobrantes del contexto. Se corrigieron conservando el tema claro inicial del HTML y el tema del sistema tras hidratar, mediante [el contrato de React para servidor e hidratación](https://react.dev/reference/react/useSyncExternalStore#adding-support-for-server-rendering); no cambia el tema nativo.
- `expo lint` reenlazó automáticamente dependencias locales. Una repetición del export falló al resolver un archivo interno existente de React Native. Se restauró la instalación con pnpm 10.33.1 y `install --frozen-lockfile`, sin cambiar versiones ni lockfile, y se reconstruyó Metro con `export --clear`. El export final de 1613 módulos, tipos, lint, scripts móviles, 102 unitarias y compilación backend vuelven a pasar. La base desechable de HTTP se detuvo y eliminó al terminar; no se tocaron otros contenedores.
